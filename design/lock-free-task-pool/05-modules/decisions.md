# 决定与可行性（L5）

## 已确认决定

- Rust 2021 与现有 Crossbeam 依赖范围不变，实际版本沿用 Cargo.lock；升级另行评估。
- 复用 SegQueue 存储，自行设计调度及串行交接，核心差异在调度而非存储。
- 串行 [(SegQueue<T>, AtomicU64); 21]；并发 [(SegQueue<T>, AtomicU64); 5]，每队列独立精确计数（用户补充）。
- serial_used 每队列3位：1位used、2位压缩任务量，共21队列、最高1位保留为0；压缩量 min(ceil(n/16),3)。weights 只放5档并发任务量，最低/低/中/高各13位、最高12位；串行平均量取消。提示恢复按源码协议；不永久隐藏以所有已开始的发布/修复最终继续并完成为前提。
- max 依据全池等待量，允许近似，不增加全局精确计数（用户确认）。
- L7 选精简档：调用链与实现切片落文档，接口契约和不变量落骨架；签名与落地分别确认。

## 被否方案

- 引入完整线程运行时：执行由外部负责。
- 只靠饱和提示判断空：可能遗漏真实任务。

## 关键交错分析及修订理由

- 否：仅在饱和恢复写零后复查。反例：提示L、计数L-1的恢复暂停；提交补到L且提示饱和同值发布；旧CAS写L-1成功，随后普通消费耗尽提示遗留1任务。因此所有成功下调后均协调只增补报，普通扣零不重建。具体协议在源码注释。
- 补报先Acquire读状态再Relaxed读计数，目标不低于当前提示，CAS失败全量重读；并发新增若在快照后发布，要么改变状态使CAS失败，要么保持更高饱和值；后续下调者亦须完成补报。允许已认领未取出的任务多报，但实际唯一取出由SegQueue保证。此为交错分析，不声称完成形式化证明或运行时验证。
- 计数先预留再队列发布、最后提示发布，避免任务先被取出而扣减未记账数量。Acquire状态读取与Release发布协调计数可见性；计数本身只记账。预发布暂停允许多报，本轮取空排除候选。
- 串行数量提示使用同样的下调后补报，used独占不因数量字段修复改变；完成只清used。同组push不重叠及快速占用覆盖整个回退，阻止后提交越过拒绝任务。
- 否：拆解句柄后手动清used。计数保护panic会跳过手动释放，故无panic拆解步骤建立私有SerialReleaseGuard；发布前展开自动释放，正常在发布后释放，所有权唯一。
- 预留后的发布与提示更新不调用外部回调、不设主动panic，分配失败沿用终止行为；不把清占用当成任务提示发布。
- 全池等待量只用于优化，压缩、预留及跨队列观察的误差用户已接受。计数半范围保护前提是实际并发预留远小于剩余半范围。

## 用户确认的进展取舍

下调者成功CAS后、补报前暂停，其他消费者可耗尽较低提示，剩余任务直到该恢复者继续才重新可见。用户明确接受所有已开始的发布/修复最终完成前提，不选择额外无候选扫描、周期探测或可帮助恢复。该设计不声称任务可见性独立于暂停线程；无锁只描述无互斥锁和CAS竞争推进，不构成更强任务进展承诺。
